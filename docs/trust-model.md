# HCPP 信任模型

**协议版本**：0.1  
**状态**：Draft  
**最后更新**：2026-09-04

---

## 1. 核心区分

HCPP 明确区分两类信任：

```text
Cryptographic Trust          ≠          Organizational Trust
（密码学信任）                            （组织信任）
```

| 类型 | 能证明什么 | 不能证明什么 |
|------|------------|--------------|
| 密码学信任 | 记录由某私钥签署；内容哈希匹配；版本链完整 | 该私钥背后的组织是否诚实、内容是否事实正确 |
| 组织信任 | 某 Publisher 经过身份验证、具备一定资质或声誉 | 单次发布的内容一定正确无误 |

HCPP v0.1 主要解决密码学信任；组织信任留待后续（DID、VC、Trust Registry 等）扩展。

---

## 2. 密码学信任提供的保证

在正确实现与密钥未泄露的前提下，HCPP 可让第三方确信：

1. **存在性**：该 ID 对应一条已注册的记录
2. **完整性**：当前看到的内容与注册时的 Content Hash 一致
3. **来源**：记录由声明的 Publisher 的私钥签署
4. **时间相关**：结合 Registry 时间戳、透明日志或公共锚定，可获得发布时间的证据
5. **历史**：可以看到完整的 Revision 链，而不是被覆盖的最新状态

---

## 3. 明确不提供的保证

HCPP **不**保证：

- 内容中的事实陈述为真
- 发布者没有错误、偏见或恶意
- 引用来源本身可信
- 具备法律意义上的版权或权属证明
- 某个 Publisher 天然值得信任

这些属于内容审核、事实核查、法律与声誉体系的范畴。

---

## 4. 信任锚点

### 4.1 Publisher 公钥

验证的起点是 Publisher 的公钥。获取公钥的可信渠道包括：

- Registry 中已注册的 Publisher 记录
- 未来的 DID 文档
- 线下或已知的安全分发渠道

如果公钥被替换且无人察觉，密码学验证仍会“通过”，但信任根基已被破坏。因此 Publisher 身份与密钥管理至关重要。

### 4.2 Registry

Registry 提供存储与查询。用户需要一定程度信任 Registry 不会：

- 隐瞒已有记录
- 伪造从未提交过的记录（在有透明日志与锚定后难度显著上升）

### 4.3 透明日志与公共锚定（后续版本）

- Merkle Proof 证明某记录包含在某 Root 中
- 公共锚定证明该 Root 在特定时间已存在

二者共同降低对单一 Registry 运营方的信任依赖。

---

## 5. 验证结果的解读

验证器应同时返回：

- 密码学结果（签名是否有效、哈希是否匹配）
- 状态信息（active / superseded / revoked 等）
- （可选）透明日志与锚定结果

示例：

```text
Signature: VALID
Content Hash: MATCHED
Status: REVOKED
Merkle Proof: VALID
Anchor: VALID
```

业务方需根据自身策略决定是否接受“签名有效但已被撤销”的记录。

---

## 6. 密钥泄露的影响

若 Publisher 私钥泄露：

- 攻击者可签署新的恶意记录
- 历史已签名记录的密码学有效性不变
- 应对措施：立即撤销该密钥、启用新密钥、必要时撤销受影响内容，并公开事件

HCPP 的设计保证“撤销密钥”与“撤销内容”是可区分的操作。

---

## 7. 未来组织信任方向

v1.0 及以后可考虑：

- Publisher 与 DID 绑定
- 使用 Verifiable Credentials 表达认证、资质
- 建立轻量 Trust Registry 或信任列表
- 与 C2PA 等生态互操作

这些机制用于回答“我是否应该信任这个 Publisher”，与密码学层互补。

---

## 8. 总结

HCPP 的定位是：

> 让来源、时间、完整性和版本关系变得**可验证**，而不是替用户判断内容真伪或发布者品德。

正确使用 HCPP 的方式是：把它作为信任链中的一环，再叠加身份、声誉、审核与领域知识等其他环节。
