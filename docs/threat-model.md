# HCPP 威胁模型（简版）

**协议版本**：0.1  
**状态**：Draft  
**最后更新**：2026-09-04

---

## 1. 目标与范围

本威胁模型关注 HCPP 协议及其典型部署中，攻击者可能破坏“可验证来源与完整性”这一核心目标的方式。

不覆盖：

- 通用 Web 应用漏洞（XSS、CSRF 等）的细节
- 物理安全、社会工程的全部形态
- 内容事实层面的虚假信息对抗

---

## 2. 资产

| 资产 | 说明 |
|------|------|
| Publisher 私钥 | 最关键，泄露可导致伪造签名 |
| Provenance Record | 来源与完整性的载体 |
| Content Hash 对应的真实内容 | 用户实际消费的对象 |
| Registry 数据 | 历史记录与状态 |
| Merkle Root / Anchor | 公共时间与包含证明 |

---

## 3. 攻击者能力假设

- 可读写公开网络流量（但无法轻易破解 TLS）
- 可能妥协部分客户端或单个 Publisher 系统
- 可能尝试攻击 Registry 服务或其数据库
- 无法轻易突破正确配置的 HSM / KMS
- 在 v0.2+ 场景下，难以在不被发现的情况下改写已锚定的 Merkle Root

---

## 4. 主要威胁与缓解

### 4.1 私钥泄露

**威胁**：攻击者获得 Publisher 私钥，签署虚假 Record。

**影响**：可伪造该 Publisher 名义下的新记录。

**缓解**：

- 私钥存于 HSM / KMS
- 支持快速密钥撤销与轮换
- 监控异常签署行为
- 必要时撤销受影响内容并公开事件

### 4.2 Registry 被篡改或隐瞒

**威胁**：运营方或入侵者修改/删除记录，或隐瞒已有记录。

**影响**：用户可能看不到真实历史，或看到被篡改的状态。

**缓解**：

- Append-only 设计
- 透明日志 + Merkle Proof（v0.2）
- 公共锚定（v0.3）
- 第三方可独立验证签名与哈希（即使 Registry 不可信，已有签名记录仍可验证）

### 4.3 内容替换（Hash 不匹配）

**威胁**：分发渠道替换了文件，但用户未校验 Hash。

**影响**：用户看到的内容与注册时不一致。

**缓解**：

- 强制或引导用户/客户端执行 Content Hash 校验
- 在分发页面显著提供“Verify Provenance”入口

### 4.4 重放与混淆

**威胁**：重放旧 Record，或将某对象的 Record 与另一内容关联。

**影响**：误导用户关于“当前有效版本”的判断。

**缓解**：

- Revision 链与 status 机制
- 验证时同时检查 status 与是否为最新 active 版本
- ID 与 Hash 分离，避免仅凭 ID 假设内容

### 4.5 算法与实现缺陷

**威胁**：弱随机数、错误的 canonicalization、有漏洞的密码学库。

**影响**：签名可被伪造或哈希可碰撞（实际难度取决于具体缺陷）。

**缓解**：

- 使用成熟密码学库
- 严格遵循 JCS 与 Content Hash 规范
- 保持依赖更新
- 官方测试向量覆盖关键路径

### 4.6 拒绝服务

**威胁**：大量注册、大对象、复杂查询导致服务不可用。

**影响**：可用性下降。

**缓解**：

- 认证与配额
- 输入大小限制
- 速率限制与监控

### 4.7 隐私泄露

**威胁**：Registry 或公开日志暴露敏感内容或个人数据。

**影响**：隐私合规风险。

**缓解**：

- 默认不存原文
- 最小化元数据
- 敏感场景仅注册 Hash
- 锚定只写 Root

---

## 5. 残留风险

- 组织层面的恶意 Publisher（密码学无法阻止“真签名假内容”）
- 用户不进行验证（工具再好也需被使用）
- 早期版本缺少透明日志与锚定时，对 Registry 的依赖更高
- UUIDv7 泄露大致创建时间（通常可接受，极端隐私场景需额外评估）

---

## 6. 总结

HCPP 通过 ID/Hash 分离、签名、append-only 历史，以及后续的透明日志与锚定，将“可验证性”建立在密码学与可公开审计的结构上，而不是单纯信任单一数据库。

实现者应重点保护私钥、严格执行规范化与签名流程，并在产品层引导用户完成验证。
