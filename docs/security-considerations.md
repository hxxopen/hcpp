## 2. 密钥管理

### 2.1 私钥保护

- Publisher 私钥 **MUST NOT** 上传至 Registry 或进入透明日志。
- 推荐使用：
  - 操作系统密钥库
  - 硬件安全模块（HSM）
  - 云 KMS
- SDK 只通过 Signer 接口使用私钥，不负责长期存储。

### 2.2 密钥轮换

- 必须支持密钥轮换，并保留历史密钥用于验证旧记录。
- 轮换过程应可审计。

### 2.3 密钥撤销

- 泄露或停用时立即标记为 revoked。
- 撤销密钥不等于自动撤销已用该密钥签署的内容；两者应分开处理。

---

## 3. 密码学算法

v0.1 选择：

| 用途 | 算法 | 备注 |
|------|------|------|
| Hash | SHA-256 | 当前可接受，未来可扩展 |
| Signature | Ed25519 | 高效、成熟 |
| Canonicalization | RFC 8785 JCS | 保证确定性 |

- 算法通过字段声明，便于未来升级。
- 已存在记录继续按原算法验证，不得因算法升级而失效。

---

## 4. 输入与规范化

- Content Hash 必须严格按规范进行规范化（去 BOM、换行归一化等），避免因实现差异导致哈希不一致。
- 签名前必须使用 JCS，禁止依赖语言默认的 JSON 序列化。
- 对用户输入做基本校验，防止异常大对象或恶意构造的 Record 导致资源耗尽。

---

## 5. Registry 安全

- 认证与授权：谁可以注册 Publisher、谁可以提交某 Publisher 的 Record，必须有明确控制。
- 传输安全：所有 API 使用 TLS。
- 完整性：优先考虑 append-only 存储与定期透明日志，降低被静默篡改的风险。
- 可用性：防止滥用注册与查询接口（速率限制、配额等）。

---

## 6. 验证端安全

- 验证器应同时检查密码学结果与状态（revoked / superseded 等）。
- 不要仅凭“签名有效”就视为业务上可接受。
- 对来自不可信渠道的 Record 保持谨慎，优先从可信 Registry 获取。

---

## 7. 隐私

- Registry 默认不存储原文、不存储不必要的个人数据。
- 敏感内容可只注册 Hash + 最小元数据。
- 公共锚定只写 Merkle Root，不写内容本身。

---

## 8. 实现建议摘要

| 项目 | 建议 |
|------|------|
| 私钥 | HSM / KMS，永不上传 Registry |
| 传输 | 强制 TLS |
| 规范化 | 严格遵循协议，使用成熟 JCS 库 |
| 状态 | 验证时同时返回密码学结果与 status |
| 日志 | 关键操作可审计 |
| 依赖 | 保持密码学库更新 |
