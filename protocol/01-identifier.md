# HCPP Protocol — Object Identifier

**协议版本**：0.1  
**文档版本**：SPEC-0.1.0  
**状态**：Draft  
**最后更新**：2026-09-04

---

## 1. 概述

HCPP Object Identifier（以下简称 ID）用于唯一标识一个被 HCPP 管理的数字对象（Artifact）。

ID 回答的问题是：

> “这是哪个对象？”

ID **不**承担内容完整性证明。内容是否发生变化由 Content Hash 负责。

---

## 2. 设计要求

ID 必须满足：

- 全球唯一
- 不依赖中心化自增序列
- 可在分布式环境中独立生成
- 适合在 URL、日志、数据库索引中使用
- 可在未来跨多个 Registry 使用
- 一旦分配，终身不变（即使对象被 supersede 或 revoke）

---

## 3. 格式规范（v0.1 规范性要求）

### 3.1 总体格式

```text
HXX-{TYPE}-{UUIDv7}
```

完整示例：

```text
HXX-ART-0198F7E3-ABCD-7EF0-89AB-CDEF01234567
HXX-RPT-0198F801-1234-7ABC-DEF0-9876543210FE
HXX-DATA-0198F812-5678-7DEF-0123-456789ABCDEF
```

### 3.2 各部分说明

| 部分     | 要求 | 说明 |
|----------|------|------|
| `HXX`    | 固定字面量 | Namespace，必须大写 |
| `TYPE`   | 大写字母缩写 | 对象类型，见第 4 节 |
| `UUIDv7` | 符合 RFC 9562 的 UUIDv7 | 必须全部大写，并**保留连字符** |

### 3.3 UUIDv7 表示规则（规范性）

- 必须使用 **UUIDv7**（时间有序）。
- 文本表示必须采用标准 8-4-4-4-12 形式。
- **所有十六进制字母必须大写**（A-F）。
- **必须保留连字符**（`-`）。
- 生成时统一转为大写；解析时大小写不敏感，实现应将输入规范化为全部大写后再存储与比较。

合法示例：

```text
0198F7E3-ABCD-7EF0-89AB-CDEF01234567
```

不推荐 / 不合法示例：

```text
0198f7e3-abcd-7ef0-89ab-cdef01234567   ← 小写（解析时应接受并规范化）
0198F7E3ABCD7EF089ABCDEF01234567       ← 缺少连字符（v0.1 不作为规范形式）
```

### 3.4 完整 ID 的 ABNF（简化）

```abnf
hcpp-id     = "HXX-" type "-" uuidv7
type        = 2*8(ALPHA)          ; 大写推荐
uuidv7      = 8HEXDIG "-" 4HEXDIG "-" 4HEXDIG "-" 4HEXDIG "-" 12HEXDIG
HEXDIG      = DIGIT / "A" / "B" / "C" / "D" / "E" / "F"
```

---

## 4. TYPE 取值

v0.1 推荐使用以下 TYPE（均为大写）：

| TYPE  | 含义       | 典型用途           |
|-------|------------|--------------------|
| ART   | article    | 文章、Newsletter   |
| RPT   | report     | 报告               |
| DOC   | document   | 通用文档           |
| PDF   | pdf        | PDF 文件           |
| IMG   | image      | 图片               |
| VID   | video      | 视频               |
| AUD   | audio      | 音频               |
| DATA  | dataset    | 数据集             |
| WEB   | webpage    | 网页               |
| SRC   | source     | 原始来源 / 引用源  |
| OTH   | other      | 其他               |

- TYPE 应简短、稳定。
- 新 TYPE 的增加属于次版本可兼容变更。
- 自定义 TYPE 时建议使用清晰的大写缩写，并避免与官方列表冲突。

---

## 5. 生成与解析要求

### 5.1 生成

实现 MUST：

1. 使用符合 RFC 9562 的 UUIDv7 生成器。
2. 将 UUIDv7 格式化为大写且带连字符的形式。
3. 与选定的 TYPE 组合成完整 ID。
4. 保证同一生成器在同一毫秒内的唯一性（UUIDv7 自身机制）。

### 5.2 解析与比较

实现 MUST：

- 接受大小写混合的输入。
- 在内部将 ID 规范化为全部大写形式。
- 比较时使用规范化后的字符串（或等价的二进制 UUID 比较）。

实现 SHOULD：

- 拒绝明显不符合 8-4-4-4-12 结构的字符串（除非明确支持宽松模式）。

### 5.3 不可变性

- ID 一旦发布，**MUST NOT** 被修改或重新分配给不同对象。
- 内容更新通过新的 Revision（可使用新的 ID 或保持同一逻辑对象下的版本链）处理，而不是改变原 ID。

---

## 6. 与其他标识的关系

- HCPP ID 是协议内的主标识。
- 未来可与 DID、DOI、现有 CMS ID 等建立映射，但映射关系不属于 ID 本身的一部分。
- ID 不隐含任何 Registry 位置信息（位置通过查询协议或配置获得）。

---

## 7. 安全性考虑

- UUIDv7 包含时间戳，会泄露大致创建时间。对于需要隐藏创建时间的场景，实现可额外评估是否使用其他版本或额外混淆层（v0.1 不强制）。
- ID 本身不是能力凭证（capability），拥有 ID 不等于拥有修改或撤销权限。
